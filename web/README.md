# web

Next.js 16 product UI (ADR-0010): dashboard, loop detail, approvals, activity feed, and a message page behind every evidence link. Server components and server actions read the ledger through `@openloop/shared`; the browser never sees AWS or Google credentials.

```
pnpm --filter @openloop/web dev     # http://localhost:3000
pnpm --filter @openloop/web build
```

Data source: with `OPENLOOP_LEDGER_TABLE` set (see `.env.example`), the DynamoDB table shared with the agent; otherwise `LocalLedgerStore` on `.openloop/ledger.json` at the repo root, created from `demo/seed-ledger.json` on first run (`OPENLOOP_LEDGER_FILE` overrides the path, `OPENLOOP_RESET=1` re-seeds).

Scan: with `OPENLOOP_RUNTIME_ARN` and the table set, the **Scan inbox** button posts to `/api/scan`, which invokes the deployed AgentCore runtime and proxies its progress stream to the browser while the runtime writes loops to the table; the dashboard refreshes as they land. A full scan takes about four minutes (`maxDuration = 300` on the route). **Check for new mail** posts `?variant=delta`, which replays the next-morning batch: the deposit and the write-up resolve, the flight gains evidence, a library loop appears. **Handle what you can** posts to `/api/handle`: the agent executes every allowed action and lists what needs the user. **Catch me up** posts to `/api/catch-up` and shows what changed since the last check, each line linking to its loop. **Approve** on a loop page marks the action approved and asks the agent to execute it (the button shows a pending state for the ~20 seconds it takes); without a runtime configured the record is only marked approved. Executed actions render what the agent produced: the draft email, the calendar event, the reminder (`components/action-effect.tsx`); cancelled and failed ones show the reason from the audit trail. The four operations live in one panel (`components/agent-panel.tsx`): the controls sit in a row beside the agent's name and when it last checked, and whatever ran last renders in a single result slot beneath them, formatted as what it is: the catch-up digest as a lead line plus items with state chips and loop links, handled actions as done and needs-you lists, a scan as a progress bar and a live log. Screenshots: `docs/screenshots/`. AWS credentials come from `~/.aws` locally and from environment variables on Vercel.

Loop page (#67): one responsibility in the order a person checks it. The header carries the state chip, the title and a facts strip (when, amount, who, any reminder, confidence). *What to do* comes first: the next action as the lead sentence, the consequence labelled "If ignored", and the buttons: "I already did this" resolves the loop and cancels what it would have left behind, while "Remind me tomorrow" and "Ignore" park it in Watching so it stops being counted in "N things need you" (`lib/park.ts`, #36). Remind sets `remindAt` a day out and shows it in the facts strip; Ignore clears it. Neither calls the agent, and neither touches proposed actions: parking says "not now", not "done". Ignore is hidden on a loop already in Watching, where it would do nothing. *What I found* lists each piece of evidence as a quote with a quiet meta line (what it did to the loop, the date, a link to the source, how sure the agent is); the left rule takes the state color of what the evidence did. *What the agent did* lists actions as cards with the artifact inside (`components/action-effect.tsx`): draft email, calendar event, reminder; proposed ones carry Approve and Decline. *History* folds any reason longer than a sentence behind a native disclosure so the agent's full rationale is one click away without dominating the page. The overview hero carries a live clock in the demo time zone (`components/live-clock.tsx`, rendered empty on the server and filled after mount).

Change banner (#39): above the hero, one or two sentences of what changed in the last 24 hours, built in `lib/changes.ts` from the audit trail and the loops' current states rather than by parsing reasons — an event says a loop changed, the loop says what it became. Only `state_changed`, `loop_created` and `action_executed` count: evidence and scans are the agent working, not a change in the world (SPEC §8H, never "you have 6 emails"). Up to two loops are named and linked, then "and N more". Nothing notable in the window means no banner at all, so a cold seeded ledger shows none and one appears after a delta run. Dismissal stores the newest counted event's timestamp in the `openloops-seen` cookie, read by the server so there is no flash, and the banner returns when something newer happens instead of staying hidden forever.

Sources: `/messages/[id]` renders one demo email or calendar event so every evidence line and source ref on a loop page links back to what the agent actually read (SPEC §12). The inbox comes from `demo/seed-inbox.json` merged with `seed-inbox-delta.json`, bundled at build time rather than read from disk; unknown ids 404.

Dashboard design (#18, #52, #61, #76): the summary is the headline, set in display type one fragment per line with each count in its state color, and each fragment links to its section (SPEC §7); the greeting sits above it as a secondary line and the lines rise in once on load, which reduced-motion turns off. State headings are 22px so the four states read as the page's structure. Compact rows give the full responsibility title room to wrap, put its requester or waiting party underneath, and align the due date and amount or action on the right. Overdue, today and tomorrow deadlines use the attention color only when the user owes a move; closed loops carry no urgency dot. Recent activity shows the latest meaningful event per responsibility, with the full history on Activity. The agent's reasoning and next-action prose live in bordered sections on the loop page. The palette is a white canvas with navy text, a navy dark theme (persistent toggle, cookie-backed, circular reveal from the button through the View Transitions API with reduced-motion and unsupported-browser fallbacks), the Teal brand, and one hue per state carried by the state heading text itself: pink Needs you, amber Waiting, blue Watching, green Resolved. Resolved stays a disclosure and opens on first load. The open-ring-and-dot mark has matching geometry in the wordmark, favicon and compact closed-share indicator (`components/loop-mark.tsx`, SVG with a single CSS draw-in that reduced-motion disables). Type is Inter with optical sizing, a 16px base, tabular figures, and a 68-character measure on source pages. Empty sections remain valid navigation destinations, and a Resolved shortcut opens its section. Desktop and 400px captures, light and dark, are in [`docs/screenshots/`](../docs/screenshots/).

Theme: the site defaults to light regardless of the device setting. The header toggle is available on every page and stores the choice in the `openloops-theme` cookie for one year; the root layout reads it so reloads render in the chosen theme immediately. The dashboard and ledger stay in Server Components; navigation, the theme toggle and agent buttons add client behavior.

Design references: [Linear’s March 2026 interface refresh](https://linear.app/changelog/2026-03-12-ui-refresh) informed navigation hierarchy and consistency; [web.dev animation performance guidance](https://web.dev/articles/animations-guide) informed restrained CSS transitions. These are implementation references, not additional architecture decisions.

`AGENTS.md` in this directory is generated by `next dev` and points agents at the bundled Next.js docs; keep it committed.
